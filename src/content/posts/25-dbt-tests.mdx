What does a passing data test really tell you? In dbt, [data tests are assertions you make about your models, and dbt ships with four generic ones: unique, not_null, accepted_values and relationships](https://docs.getdbt.com/docs/build/data-tests). They check that the records are well formed and agree with each other.

## What the data tests said

Store 014's dbt project runs the 32 data tests from the series' technical companions on June's records: 31 pass, and the other warns that the full-cream milk book goes below zero on six days. By those tests, June was a clean month.

## What the domain tests found

Thirteen domain tests check the same records against how a store, a warehouse and UPI work, and every one fails on June, as a warning that keeps its failing rows. Let me share four of them:

- No item goes longer without a sale than its usual rate allows while the books show stock: 10 rows, the silences that mark an empty shelf.
- Something other than the pick checks what is on each pallet: 30 rows, every pallet in June.
- No count correction has a mirror image in the same building: 3 rows, the mis-pick and the milk scan errors.
- Every success in the provider's report has an approved payment: 26 rows, the extra charges.

**31 of 32 data tests passed, and all 13 domain tests failed.**

## Why the data tests pass

Eight of the twelve joins between June's records always agree, because one record was copied from the other. A test on a copy can only pass.

A domain test joins a record to something that looks at the world: a count, a shelf audit, the payment provider's report, or the till's usual rhythm. That join is where the failures show.

## Run it

```bash
pip install dbt-duckdb
unzip store-014-dbt.zip && cd store-014-dbt
dbt build --profiles-dir .
```

The project comes with the records and runs on DuckDB. The gap detector the retail companion runs in Python is written in SQL here, and finds the same ten silences, and a model called join_agreement counts how often each join agrees.

## Write your own

Pick one KPI your agents act on. Write down the record it reads and one observation that could contradict it, then write the test that joins them, set to warn and to keep its failing rows. The domain layer template has one filled-in example for each part.
