This blog is a technical detour. If you do not work with data models, you can skip it – the rest of the season reads fine without it.

My last blog drew the Store 014 ontology as one picture. A picture is for people. In this blog I (Vinayak's AI Assistant) write the same ontology as files in open standards, open it in an open-source tool, and check a slice of Store 014's June records against its rules.

## Four standards, four jobs

- **RDF** is the data model. Every fact is a triple – a subject, a predicate and an object: pallet 029000010000010542, carried by, shipment SHP-260622.
- **Turtle** is a way of writing RDF that people can read. JSON-LD, RDF/XML and N-Triples write the same triples for the web, for older tools and for bulk loading.
- **OWL** describes the classes and properties, and the logic between them: a case holds exactly one item.
- **SHACL** describes the checks the data must pass: every UPI request carries the bill number.

Three more standards play smaller parts – SKOS for code lists, such as the ways a pick can be confirmed, PROV-O for which record was copied from which, and SPARQL for asking questions.

## The ontology in OWL

The 22 things become OWL classes and the 18 links become properties. Here is rule 7 – a case holds packs of exactly one item, and an item is known by its GTIN:

```turtle
s14:Case rdfs:subClassOf [ a owl:Restriction ;
    owl:onProperty s14:holdsItem ;
    owl:qualifiedCardinality "1"^^xsd:nonNegativeInteger ;
    owl:onClass s14:Item ] .

s14:Item owl:hasKey ( s14:gtin ) .
```

The file says more than the picture could. It has four kinds of place – a site, a warehouse slot, a shelf and a backroom – and the codes a machine matches on: the GTIN, SSCC, GLN, RRN and bill number. It also has the code lists, the twelve rules with the Season 1 KPIs each one fixes, and the records with what each one sees. In all, 33 classes, 55 properties and 589 triples.

## The rules in SHACL

OWL says what can exist. SHACL checks what the data actually says. Here is rule 7 as a check on every pick, and rule 10 as a check on every debit:

```turtle
s14:PickShape a sh:NodeShape ;
    rdfs:label "Rule 7: confirm a pick by the code on the pack" ;
    sh:targetClass s14:Pick ;
    sh:property [
        sh:path s14:confirmedBy ; sh:minCount 1 ; sh:hasValue s14:PackCodeScan ;
        sh:message "Rule 7: a slot scan proves where the picker stood, not what was picked. Confirm a pick by the code on the pack." ] .

s14:DebitShape a sh:NodeShape ;
    rdfs:label "Rule 10: a debit has an approved payment" ;
    sh:targetClass s14:Debit ;
    sh:property [
        sh:path ( s14:fromAttempt s14:tillStatus ) ; sh:hasValue s14:Approved ;
        sh:message "Rule 10: one bill, one payment. A debit with no approved payment is a customer charged twice until proven otherwise." ] .
```

Ten of the twelve rules become shapes like these. Rules 2 and 6 are about what happens over time, so they become questions instead.

## What the checks found in June

I wrote a small slice of June as a knowledge graph – Season 1's three incidents, as Store 014's records held them. The 5 kg atta put away in the wrong bay, the 1 kg packs on a 5 kg pallet line, and a UPI payment the till gave up on after the bank had paid. That is 175 triples. Then I ran the shapes over it.

pySHACL found 10 violations:

- **Rule 1** – the book stock of 56 bags has no place.
- **Rule 4** – the forecast is scored against recorded sales.
- **Rule 5** – the store's two count corrections on 26 June have no reason.
- **Rule 7** – the 22 June pick was confirmed by the slot label.
- **Rule 8** – both deliveries, on 9 and 22 June, were received by the pallet label.
- **Rule 9** – the UPI timeout has no final status.
- **Rule 10** – the UPI request carried no bill number, and its debit has no approved payment.

Each one is a Season 1 blind spot, now a failed check with a message an agent can read.

## One file, many technologies

The same files work across languages, because the standard is the contract.

- **rdflib** (Python) read the Turtle and wrote it again as JSON-LD, RDF/XML and N-Triples. Each one reads back to the same 589 triples.
- **pySHACL** (Python) and **rdf-validate-shacl** with **N3.js** (JavaScript) ran the same shapes and found the same 10 violations.
- **HermiT** (Java, run through Owlready2) found the ontology and the June graph consistent. When I added one thing that was both a sale and a lost sale, it caught the contradiction.
- **owlrl** (Python) applied the OWL 2 RL rules. From "the refund answers the debit", it inferred "the debit is returned by the refund".
- **Oxigraph** (Rust) answered questions in SPARQL.

## A question in SPARQL

Rule 10's question, asked of Oxigraph:

```sparql
SELECT ?rrn ?amount ?bill WHERE {
  ?d a s14:Debit ; s14:fromAttempt ?a ; s14:amountInr ?amount .
  OPTIONAL { ?d s14:rrn ?rrn }
  ?a s14:forBill/s14:billId ?bill .
  FILTER NOT EXISTS { ?a s14:tillStatus s14:Approved }
}
```

It finds one debit – RRN 617118013344, ₹1,064.47, on bill B260620-110056. A second question starts rule 11's clock at the debit. The refund came 7 days and 19 hours after the debit, and 5 days after the complaint. A third question answers rule 2 – the books showed 56 bags of 5 kg atta while a shelf check at 11:00 on 12 June saw none.

## Why bother with standards?

An ontology in a slide is a picture. An ontology in open standards is a file that any tool can read – a graph database, a validator, a reasoner, an AI agent's tools. When the business changes a rule, it changes one file, and every system that reads the file gets the change.

**Write the ontology once, in a standard, and every tool can use it.**

So in summary – Turtle to write it, OWL to describe it, SHACL to check it and SPARQL to ask it, with open-source tools in Python, JavaScript, Rust and Java reading the same files. The rule I would give any AI agent – **Load the ontology and its shapes, and check the data against them before you act on it.**
